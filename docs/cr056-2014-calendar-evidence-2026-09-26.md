# CR-056 实录：2014 年休市公告、检索边界的更正与 2015 训练下限的归属（2026-09-26）

分支 `algorithm/rl-long-window`，范围仅 `services/algorithms/**` 加根 SDD 与本文件。
触发原因是一句用户指认：「`https://www.sse.com.cn/disclosure/dealinstruc/closed/list/`
的第六页难道不是有 13 到 14 年的吗？」——有。CR-054/CR-055 写在风险清单里的
"2015 年之前仍无证据"因此被就地更正。

## 1. 结论

| 年份 | 采用的公告 | 公告口径休市工作日 | 表内 | 差异 | basis |
| --- | --- | --- | --- | --- | --- |
| 2014 | 年度通知（2013-12-25）+ 专项 〔2014〕2/4/6/10号 | 16 | 16 | 双向 0 | `official-notice`（新增） |

2015—2024 十年的 `closures` 与元数据一条未动：复算前后每年的公告休市工作日数
（17/17/16/18/17/19/18/18/18/20）与 CR-055 记录逐一相同，2015-01-05→2024-12-31 的
期望交易日仍是 2431 根。所以本轮和 CR-054/055 一样**不触发重填、不触发重训**，
已产出的四份研究权重与 manifest 继续有效。

用它翻不到 2012 年；我不猜 URL。所以 2013—2012 的缺口这次是**交易所在线归档不可得**，
要补只能靠纸面公告或其他官方渠道，闸门行为不变（继续 `CalendarUnavailableError`）。

## 3. 年度通知不带文号时怎么写引用

2014 年的年度通知页面上**没有文号**，正文只有落款"二○一三年十二月二十五日"；它的
四份专项公告都把它引作《关于上海证券交易所2014年全年休市安排的通知》（上证函〔2013〕269号）。

CR-054/055 的引用格式是"标题+文号+发布日+URL"，复算工具和 network 用例都按这个形状
回抓并断言文号出现在页面上。为凑格式给这份通知写一个页面里不存在的文号，等于给
复核工具喂伪证——它会把"我编的文号"当成"页面确实如此"来通过。所以：

- 记录里写"（2013-12-25 发布）URL"，并另起一条说明"页面本身未标注文号"，
  同时给出四份专项公告对它的上证函引用作为身份佐证；
- 复算工具的 `CITATION` 从"必须带上证公告文号"改为通用三段式（标题 + 括注 + URL），
  锚定年份**优先取标题年份**、无标题年份（如「…70周年纪念日休市安排的公告」）再取
  文号年份；
- network 用例同样只在记录的括注里出现文号时才核对文号。

改完先复算再改数据：通用化之后、写入 2014 之前，十年输出与 CR-055 完全一致
（13 份公告、逐年数字不变），这才允许新增年份入库。

## 4. HISTORY_FLOOR 不动：需求边界不是日历的副产品

`splits.py` 里那句注释写的是"更早的K线需要一份我们未逐年核对的休市日历"，把
`HISTORY_FLOOR = 2015-01-01` 讲成了日历缺口的替代品。日历现在核到 2014，这条注释就
成了错误的因果——照它推理，今天该把下限挪到 2014，而 REQ-11 与助教口径都是
"**训练起点不早于 2015**"。所以本轮：

- `HISTORY_FLOOR` 保持 2015-01-01，注释改为真实理由（下限来自 REQ-11 本身；
  日历自 CR-056 起已核到 2014）；
- 想让训练真的跨过 2014，需要一次单独授权同时做两件事：放宽 REQ-11 的窗口规则、
  回填 2014 年K线（研究目录当前只到 2015-01-05→2024-12-31）。本轮两件都不做。

这是"需求边界"和"完整性红线"不得互相顶替的一个具体例子（D-12）。

## 8. 审查官复核与推送（2026-09-26 同日追加）

用户指令：以代码指令审查官身份对 CR-056 新增代码做逻辑审查，并写临时测试文件
钉桩验证。执行方式：一次性脚本 `services/algorithms/tmp_audit_cr056_logic.py`
（离线、无网络），命令
`PYTHONUTF8=1 .venv/Scripts/python.exe tmp_audit_cr056_logic.py`，两轮运行均
`AUDIT OK — 全部钉桩通过`，随后删除脚本，`git status` 干净。

钉住的事实（全部通过）：

- 证据表：2014 条目 9 区间有序不重叠、展开 16 个工作日休市；审计字段齐全；
  全表 11 年过 `_validate_evidence`，basis 均为 `official-notice`；
- 日历 API：`closure_basis(2014)=="official-notice"`、`closure_basis(2013) is None`、
  `is_session(2013-12-31)` 抛 `CalendarUnavailableError`；交易日黄金值 2014=245、
  2015–2024=2431；逐年休市工作日 16/17/16/18/17/19/18/18/18/18/20；
- 引注解析：全表 21 条、2014 的 5 条全锚 2014；"标题年份优先于文号年份"用合成
  条目（标题 2015年 + 文号〔2014〕15号 → 锚 2015）与真实 2015 条目（2 条全锚
  2015）双重钉住；
- RL/深历史门：`HISTORY_FLOOR` 仍 2015-01-01，`Split(2014-01-01,…)` 照旧拒绝；
  `preflight(2014..2024)` ready、`preflight(2013..)` 拒绝且
  `unverifiedYears==[2013]`；
- 防线：证据文件覆盖内置 2025 被拒；`cross-validated` 缺审计字段被拒。

审查发现（均为既有现状，非 CR-056 回归，建议与已搁置的 RL 训练器缺陷同批立
后续 CR 处理）：

1. `recheck_official_closures.cited_notices` 的 `anchor()` 返回 None 时静默丢弃该条
   引注（fail-open）：若未来某年引了一份标题无年份且无文号的公告，复算工具不会
   核对它。建议对"引注出现次数 vs 返回条数"加守恒检查；
2. `test_deep_history_probe.py` 的文号前缀是封闭集（上证公告|上证函|证监办发），
   其他文号（如上证交字〔2012〕205号）会漏配，2014–2024 实测不受影响；
3. `calendar.py` 的 MM-DD 区间无法表达跨年休市（既有设计），如出现 12-31→01-02
   需拆两条记录，当前表不受影响。

裁决：CR-056 新增代码逻辑自洽、防线未松动，唯一行为变化是 2014 以官方公告口径
进入已核对年份，与登记范围一致；维持已提交状态，无需返工。据此用户授权推送，
`git push -u origin algorithm/rl-long-window`（新建远端分支，基线 = 远端 main
